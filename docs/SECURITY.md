# Security review — 2 October 2026

**Deployment decision: serve only the static portfolio on Vercel. Do not expose the historical Sinatra application.**

The reviewed deployment creates no server functions, API, account system, uploads, database access, external connections, or homelab route. That removes the application-to-homelab attack path for this project. It does not certify the rest of the homelab or its two existing public services; neither was accessed, scanned, or reconfigured.

## Scope and method

Reviewed the original routes, model authorization and authentication, session setup, upload handling, seed/setup scripts, dependency lockfile, and relevant templates. Reviewed the new browser state model, persistence, role views, tour, build output, and Vercel configuration. A Luna reviewer independently checked the architecture, workflow rules, tour isolation, and deployment exclusions. Automated checks exercise local production responses and real browser behavior. The existing Vercel authentication also allowed verification of an actual protected preview.

No old application server was started, and no coursework database was initialized or modified. The startup guard was checked separately from application loading. Dependency checks inspect lockfiles, not the user database.

## Public surface and controls

| Surface                | Treatment                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/` and bundled assets | Static HTML, JS, CSS, locally hosted fonts, and a favicon only                                                                                         |
| Demo routes            | URL fragments interpreted in the browser; no HTTP route handlers                                                                                       |
| Data and identities    | Fresh synthetic records using reserved `example.org` contacts; no original database, CSV names, or uploaded images reused                              |
| Input                  | React text rendering; no `dangerouslySetInnerHTML`, HTML injection, executable templates, or user-controlled URLs                                      |
| Saved state            | A versioned, schema-validated action log, capped at 400 actions / 200,000 characters, replayed through business rules; malformed data resets safely    |
| Persistence failure    | An in-memory session and visible notice; browsing and reset still work                                                                                 |
| Guided tour            | Separate in-memory state; free exploration restored on exit                                                                                            |
| Network                | CSP `connect-src 'none'`; no fetch, WebSocket, analytics, or external images/fonts                                                                     |
| Scripts and styles     | Same-origin assets only, without `unsafe-inline` or `unsafe-eval`; validation runs without runtime code generation                                     |
| Browser hardening      | CSP denies objects, frames, workers, form navigation, and base changes; `nosniff`, `DENY`, no-referrer, restricted permissions, COOP, and HSTS headers |
| Deployment context     | `.vercelignore` allowlists only build inputs; `publicDir: 'assets'`; fixed `dist/` output; no proxy or catch-all rewrite                               |
| Build regression check | Rejects unexpected asset types/paths, source maps, private endpoint strings, database references, missing CSP rules, rewrites, and functions           |
| Local servers          | Bound to `127.0.0.1`; production preview serves only build files and supports GET/HEAD                                                                 |

The role picker is a simulation, not authentication. All fixture records are available in the downloaded JavaScript, including the names hidden by the UI. Browser storage is user-editable and can be copied by browser tab duplication or session restore. There are no real credentials or private records to protect in it. Visitors should use fictional input; local text may remain until reset or the browser discards the tab’s session.

The absence of an API is the principal boundary. CSP is additional protection, not a substitute for excluding the backend. If a future change adds real accounts or network calls, this review no longer covers that deployment.

## Historical application findings

These findings remain in the coursework implementation. Their public risk is contained by excluding the implementation from Vercel and refusing ordinary/production startup. The archived backend is not represented as repaired or safe to publish.

| Severity if exposed | Finding and evidence                                                                                                                                                                                                                                                                                                      | Required treatment before any future backend release                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Critical            | `controllers/profile.rb` accepts a submitted `role` and assigns it to the current user. The profile edit view offers an administrator role. A signed-in user can escalate privileges.                                                                                                                                     | Fixed allowlists for editable fields; server-side role assignment restricted to authorized administrators.                                       |
| Critical            | `controllers/manageAccounts.rb` checks only `logged_in` on account management, deletion, reassignment, global capacity, and semester-date mutations.                                                                                                                                                                      | Centralized role/ownership checks for every route and negative authorization tests.                                                              |
| Critical            | `models/authentication.rb` derives an AES-CBC key from a supplied password, decrypts a stored user ID, but never compares the plaintext with the expected ID. A wrong key that happens to produce valid padding is accepted by this check. Null ciphertext skips verification entirely for an otherwise approved account. | Replace the custom verifier with a maintained password hashing library and verified reset/migration flow; reject missing verifiers.              |
| High                | Public `/signup/admin` can request an admin role; its initial authentication record deliberately lacks a verifier. Approval and first-login/password setup are not a sound authorization boundary.                                                                                                                        | Remove public admin enrollment; use an authenticated invitation/provisioning workflow and tested first-login rules.                              |
| High                | `GET /profile/edit?id=…` loads another person’s profile and changes their first-login state without ownership checks. `Match.exists?` considers any match status for profile visibility.                                                                                                                                  | Enforce self/admin ownership and active-match visibility on every relevant read/write.                                                           |
| High                | Account approval/denial mutate state through GET routes in `controllers/approvals.rb`. No application CSRF token checks were found in the form workflow; framework defaults do not make state-changing GET safe.                                                                                                          | POST-only state changes, synchronizer tokens or equivalent, origin checks, and secure cookie settings.                                           |
| High                | The historical lockfile matches known advisories affecting Rack, sessions, Puma, Sinatra and other libraries; see the dependency report below.                                                                                                                                                                            | Upgrade and retest the entire runtime before exposure. No blanket exception list.                                                                |
| Medium              | Upload validation checks only filename extension and size in `helpers/validation.rb`; uploaded bytes are placed under the public static root before all profile validation finishes. Existing images can be requested independently of profile privacy.                                                                   | Decode/re-encode accepted images, isolate storage, authorize access, and enforce parser/proxy/body limits before accepting uploads.              |
| Medium              | Profile biography output is unescaped in `views/profile.erb` and `views/profileEdit.erb`. A character denylist in the controller is not a complete output-encoding strategy.                                                                                                                                              | Escape at every HTML sink and remove input filtering as the primary XSS defense. This review did not prove a bypass of every current input path. |
| Medium              | Debug output includes submitted parameters/user objects, test credentials are predictable, `db/db.rb` forces the test environment, and setup scripts replace databases.                                                                                                                                                   | Remove sensitive logging, segregate environments, eliminate default credentials, and make setup explicit and non-destructive.                    |

For accuracy: the legacy cipher stores an encrypted **user ID**, not an encrypted plaintext password. The defect is unsafe verification, including acceptance based on padding and absent ciphertext. [OWASP recommends established password hashing](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). [OWASP’s CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) also covers why state-changing GET requests and incomplete token protections are unsuitable.

`scripts/legacy_safety.rb` aborts before loading Sinatra for production (`APP_ENV` or `RACK_ENV`) and any `VERCEL` environment. Normal startup is disabled unless deliberately enabled with `UNICONNECT_LEGACY_LOCAL=1`; historical tests can load only when both app and Rack environments are `test`. An allowed legacy server defaults to loopback. This is an accident-prevention guard, not a sandbox: someone deliberately bypassing it or forwarding its local port can still expose vulnerable code.

## Dependency and credential checks

- **Public application:** `npm audit --audit-level=moderate` reported **0 known advisories**, including development dependencies, at the time of review. Versions are pinned in `package-lock.json`.
- **Archived Ruby application:** `bundler-audit 0.9.3`, with Ruby Advisory Database commit `cb6460a5876f3bf6ef908718457bfa9dd4ca9c06`, reported **51 unique package/advisory matches across 10 gems**. The scanner emitted 179 records because platform-specific lock entries repeat findings. The deduplicated evidence and lockfile hash are saved in [legacy-dependencies.json](legacy-dependencies.json). A matching version is not proof that every advisory is exploitable through this app; none of these gems are installed or served by the portfolio deployment.
- **Credentials:** a targeted working-tree scan found no private-key blocks, GitHub token patterns, AWS access-key IDs, live Stripe keys, OpenAI project-key patterns, or Tailscale auth-key patterns in tracked text files. Known fixture passwords remain in the excluded coursework source. This was not an exhaustive Git-history or entropy-based secret scan.

## Verification and remaining limits

The final clean-install check passed on **Node.js 24.21.0**: **24 model tests and 18 desktop/mobile browser tests**, strict TypeScript compilation, and the production build audit. Automated accessibility checks reported no violations on the 11 main role/page combinations checked in each viewport and on the tested dialog/tour. Layout checks also passed at a 320-pixel viewport. The output contains seven allowed static files, including third-party license notices.

Model tests cover application duplication, invalid input, role rules, capacity races at acceptance, competing requests, waitlist eligibility, privacy transitions, support decision types, account flags, capacity settings, semester closure, notification ownership, and malformed/oversized saved data.

Production-browser tests cover the complete request → acceptance → withdrawal → admin decision flow, tour action/skip behavior and restoration, profile edits, filters, reset, tab isolation, storage denial, desktop/mobile layouts, automated WCAG checks, keyboard dialog focus, no external runtime requests, strict CSP, and inaccessible legacy paths. `npm run build` audits the output files. These checks do not replace manual assistive-technology testing or constitute a guarantee against all future vulnerabilities.

The actual Vercel upload dry run includes only **28 approved build inputs**; see [deployment-inputs.json](deployment-inputs.json). The deployed preview reports no functions, serves the expected HTML/JS/CSS byte for byte, and includes every configured security header on the root, tested assets, and missing paths. The six legacy/private paths listed in [DEPLOYMENT.md](DEPLOYMENT.md) return 404 after passing deployment protection. The eight-step tour also completed in desktop and mobile Chromium against that hosted preview, with zero runtime errors or external requests. Sanitized results are saved in [hosted-verification.json](hosted-verification.json).

The retained preview requires Vercel sign-in, and optional toolbar injection is disabled for this project. The temporary project-specific automation bypass used for verification was revoked. Vercel's automatic first production deployment was removed; the former production URL returns 404. No changes were made to existing projects or Funnel services. See [DEPLOYMENT.md](DEPLOYMENT.md) for the deployment record and future publishing steps.

The homelab’s operating system, networking rules, other applications, and historical Git data are outside this review. These checks establish the reviewed deployment's boundary, not a guarantee against every future vulnerability. The chosen architecture adds no homelab exposure and requires no Funnel changes.
